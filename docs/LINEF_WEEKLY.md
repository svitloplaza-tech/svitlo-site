# Щотижневе оновлення LineF (рішення власника 06.11.2026: раз на тиждень)

Запускає запланована задача «LineF: наявність і ціни щотижня» (понеділок ~03:47 за Києвом).
З 09.11.2026 — без тимчасової таблиці tmp_stock: перевірка безпеки блокувала створення таблиці з доступом anon на живій базі.

1. `pip install requests --break-system-packages` (якщо треба) і `python3 scripts/linef_stock.py scrape` (≈10–25 хв).
2. `python3 scripts/linef_stock.py sql` — порівнює з поточними даними сайту і пише `scripts/out/linef_update.sql`
   лише з позиціями, що змінились (зазвичай кілька сотень рядків).
   - «СТОП: помилок … (>20%)» → НІЧОГО не оновлювати, повідомити власника.
   - «змін немає» → оновлювати нічого, звіт власнику: змін немає.
3. Виконати вміст `scripts/out/linef_update.sql` ОДНИМ викликом execute_sql (Supabase, проєкт teidqxvftoihhwmubiyf).
   Якщо файл завеликий для одного виклику — розбити VALUES на частини й виконати кожну тим самим запитом.
   Логіка в SQL: ціна LineF = роздріб LineF (price = price_supplier); зміну ціни більш ніж удвічі (або менш ніж наполовину)
   НЕ застосовувати — лише показати у звіті як підозрілу; якщо нова ціна ≥ old_price — old_price обнулити.
   Ціни Колекції (supplier ≠ LineF) не чіпаються.
4. Звіт власнику з результату запиту: скільки змінилось наявності (з'явилось / зникло / очікується), скільки сторінок не відкрилось
   (вивід кроку 2), скільки цін оновлено (up / down), топ-5 змін ціни, підозрілі (не застосовані).

Запасний варіант, якщо execute_sql недоступний: надіслати власнику `scripts/out/linef_update.sql`, він виконує його в Supabase → SQL Editor
і присилає рядок результату.
Сайт підхоплює нові дані сам протягом ~3 год (кеш каталогу).
